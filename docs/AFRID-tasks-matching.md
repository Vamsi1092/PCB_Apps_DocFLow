# DocFlow — Backend Tasks for Afrid: Real 2-Way / 3-Way Matching

**From:** Vamsi (frontend)
**To:** Afrid (backend / database)
**Last updated:** 2026-07-24

**Goal:** After these tasks, the DocFlow UI shows **genuine** PO / GRN / Invoice
matching and exception summaries — with **no frontend changes needed** — instead of
today's placeholder, where "3-Way Matched" really means the invoice was matched
against a copy of itself.

---

## The problem in one paragraph

There are three separate PO/GRN datasets in the database, and **none of them is the
real one** driving the UI's match badges:

| Dataset | What it actually is | Who reads it |
|---|---|---|
| `purchase_orders` / `goods_receipts` (+ lines) | Old **synthetic seed data** (13 POs, 12 GRNs, deterministic `20000000-…` UUIDs, all the same `created_at`). PO numbers like `PO-21078-A` match no real invoice. | Nothing. Dead weight. |
| `reference_purchase_orders` / `reference_goods_receipts` (+ lines) | **Auto-generated by cloning each invoice's own header/lines** — `generate_reference_purchase_order()` literally copies the invoice's `total_amount`/lines into a new "PO" tagged *"AI Generated Reference PO"*; the GRN clone sets `accepted_quantity = ordered_quantity` (a fictional perfect receipt). | **This is what `validate_document()` compares against today** — so matching validates the *engine*, not real reconciliation. |
| `document_chains` + `ap_documents.document_chain_id` | The **real** linkage — DB triggers auto-group same-PO-number documents (Invoice / PO / Ack / GRN) into a chain, no app code. This is what the Worklist Lifecycle popup renders. | **Not connected to `validate_document()` at all.** |

So the Lifecycle popup honestly shows "Not Received" for PO/Ack/GRN (no such email
arrived), while the same invoice can show "3-Way Matched" elsewhere (because the
reference-clone was generated) — two facts that currently have nothing to do with
each other. The tasks below connect the **real chain** to **real matching** and
expose it through the views the frontend already reads.

**Live counts (last checked):** `ap_documents` 113 · `invoice_headers` 52 ·
`document_chains` 23 · `reference_purchase_orders` 7 · `validation_runs` 8 ·
`validation_results` 348.

## Task 1 — Create the matching table `document_match_records`

One row per invoice's current match attempt. This is the shape that makes 2-way /
3-way trivial to render in the UI.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `document_chain_id` | uuid FK → `document_chains.id` | Anchors this row to the **real** chain, not a clone. |
| `invoice_document_id` | uuid FK → `ap_documents.id` | |
| `po_document_id` | uuid null FK → `ap_documents.id` | The real PO document in this chain, if one has arrived. Null = not received. |
| `grn_document_id` | uuid null FK → `ap_documents.id` | The real GRN document in this chain, if one has arrived. |
| `invoice_number` | text null | |
| `po_number` | text null | |
| `grn_number` | text null | |
| `invoice_data` | jsonb null | Invoice header + lines (already exists in `invoice_headers`/`invoice_lines` — mirror or reference it here so the UI can read everything from one row). |
| `po_data` | jsonb null | PO header + lines — populated by Task 2. |
| `grn_data` | jsonb null | GRN header + lines — populated by Task 2. |
| `match_status_invoice_po` | text null | The **2-way** verdict (Invoice ↔ PO). Enum: `MATCHED / VARIANCE / UNMATCHED / NOT_AVAILABLE`. |
| `match_status_invoice_grn` | text null | The extra check **3-way** needs (Invoice ↔ GRN). Same enum + `NOT_APPLICABLE` when there is no GRN. |
| `match_status_po_grn` | text null | PO ↔ GRN reconciliation (ordered vs. received). Same enum. |
| `overall_match_type` | text null | `2_WAY / 3_WAY / UNMATCHED` — **same vocabulary** as today's `current_match_results.match_type`. |
| `overall_match_status` | text null | `MATCHED / VARIANCE / UNMATCHED` — **same** as `current_match_results.match_status`. |
| `exception_summary` | text null | Human-readable rollup, generated whenever any status above is `VARIANCE` / `UNMATCHED`. E.g. *"Invoice qty 50 vs PO qty 45 — 5-unit variance; GRN confirms 45 received."* |
| `engine_version` | text | Same pattern as `validation_runs.engine_version`. |
| `created_at` / `updated_at` | timestamptz | |

**✅ Done when:** the table exists and RLS lets the anon role `SELECT` it (same read
access as the other tables the UI uses).

## Task 2 — Extract real PO & GRN documents into structured data

Today only **invoices** get structural extraction (`invoice_headers` /
`invoice_lines`). PO and GRN documents already arrive as email attachments —
`email_attachments.detected_type` already includes values like `"Purchase Order"`
and `"GRN"` — but nothing parses them into header/line data.

- Extend the OCI extraction pipeline to parse PO and GRN attachments into header +
  line structures, and store them as `po_data` / `grn_data` on the matching row.
- Keep this **per real ingested document** — **not** in the master-data-shaped
  `purchase_orders` / `goods_receipts` tables (those aren't shaped for per-document
  data).

**✅ Done when:** for a chain where a real PO/GRN email has arrived, `po_data` /
`grn_data` hold **that document's actual extracted numbers**, not a copy of the
invoice's.

---

## Task 3 — Point the matching engine at the real chain, not the clones

- In `validate_document()` (`app/services/validation_service.py`), look up the
  invoice's real PO/GRN via `ap_documents.document_chain_id` (already computed
  automatically by the triggers) instead of `reference_purchase_orders` /
  `reference_goods_receipts`.
- `validate_invoice_data()` is already **generic over header/line dicts**, so it
  likely doesn't need to change — only its **data source** does.
- Write the three per-pair statuses, the two overall fields, and the
  `exception_summary` into `document_match_records`.

**✅ Done when:** a document with no real PO in its chain reads `UNMATCHED` (honest),
and one with a real PO (and GRN) reads `2_WAY` / `3_WAY` with statuses computed from
**real** extracted data.

---

## Task 4 — Generate the exception summary on mismatch

Whenever any of the three pair-statuses is `VARIANCE` or `UNMATCHED`, populate
`exception_summary` with a one- or two-sentence human explanation of what didn't
reconcile: **which field**, the **invoice value vs. the PO/GRN value**, and the
**delta**. This is exactly what Document Review's "Exception Summary" panel displays.

**✅ Done when:** a mismatched document has a readable `exception_summary`; a clean
match leaves it null/empty.

---

## Task 5 — Feed the existing views so the UI needs ZERO changes

The frontend already reads matching through two existing views:

- **`document_ui_view`** → `.match_type`, `.match_status`, `.failed_check_count`
- **`document_lifecycle_view`** → the PO → Ack → GRN → Invoice chain

Both are backed today by `current_match_results` → `validation_runs` /
`validation_results`.

- Make `current_match_results` (and therefore `document_ui_view`) resolve from
  `document_match_records` (real data) instead of the clone path.
- Either keep `validation_runs` / `validation_results` as the backing and just
  repoint their data source (Task 3), **or** make `document_match_records` the
  source of truth that `current_match_results` reads from — **your call**, as long
  as `document_ui_view` ends up populated from real matching.

**✅ Done when:** `document_ui_view.match_type` / `match_status` for a real document
reflect real matching. **At that point the UI shows real 2-way / 3-way with no
frontend change whatsoever.**

---

## Task 6 — Retire (or clearly demote) the clone path

Once Tasks 2–3 work, stop generating `reference_purchase_orders` /
`reference_goods_receipts` as if they were real — either remove that generation, or
keep it explicitly as a **demo-only fallback that never reports as genuinely
`MATCHED`**. Leave the old `purchase_orders` / `goods_receipts` seed tables alone
(nothing reads them) or drop them.

**✅ Done when:** nothing in the live match path reads a cloned reference row as a
real match.

needed there. The remaining **17** split into two fixes:

1. **4 rows have a malformed `storage_path`** — literally `downloads\854552 -A.pdf`

   **Do:** re-upload these 4 files and set `email_attachments.storage_path` to a
   valid forward-slash key (`{uuid}/{filename}`), matching the working 96.
2. **13 rows have no attachment at all** (`storage_bucket` / `storage_path` /
   `filename` all null) — mostly synthetic seed rows (`50000000-0000-…` UUIDs), plus
   a few real ack / GRN / credit-memo / invoice docs.
   **Do:** confirm which of these 13 are real documents that should have a file, and
   backfill Storage for those.

**✅ Done when:** the 4 malformed paths preview correctly, and the real documents
among the 13 nulls have attachments.

## Acceptance — how to verify end-to-end

1. Pick a chain that has a real **PO** (and ideally **GRN**) email plus the invoice.
2. Confirm `document_match_records` has a row with real `po_data` / `grn_data`,
   correct per-pair statuses, `overall_match_type`, and (if mismatched) an
   `exception_summary`.
3. Confirm `document_ui_view` for that invoice returns the same `match_type` /
   `match_status`.
4. In the UI (no code change):
   - Worklist **Lifecycle popup** shows the PO/GRN as received,
   - the **match badge** shows real 2-way / 3-way,
   - Document Review's **Exception Summary** shows the real `exception_summary`.
